## 🧭 Navigation Guidelines for Agents & Developers

- **Making Architectural / Cross-Cutting Changes**: Always read [`architecture.md`](./architecture.md), [`execution-flow.md`](./execution-flow.md), and [`decisions.md`](./decisions.md) before proposing changes to data flow or message schemas.
- **Adding / Modifying Action Steps**: Consult [`actions.md`](./actions.md), [`idempotency.md`](./idempotency.md), and [`worker.md`](./worker.md).
- **Extending Messaging / Queuing**: Review [`kafka.md`](./kafka.md) and [`worker.md`](./worker.md).
- **AI Implementation**: Start with the [Autonomous DLQ Triage master plan](./ai-dlq-master-plan.md) and [failure taxonomy](./AI/failure-taxonomy.md). The AI service uses TypeScript, Bun, Express, Zod and LangGraph.js inside the existing monorepo; the backend, worker, Kafka infrastructure and frontend keep their current responsibilities. AI reference material uses `docs/AI/` (do not create a parallel `docs/ai/` directory). ADRs 009–019 in [decisions.md](./decisions.md) distinguish implemented foundations from proposed integration details.
- **AI triage boundary**: Phases 4A–4C provide the implemented read-only, owner-scoped evidence path, Phase 5 adds six simulated runbooks with bounded deterministic retrieval, and Phase 6 implements the bounded transient diagnosis graph (`POST /api/v1/triage/diagnose`). Phase 9 recovery is verified with real PostgreSQL/Kafka and stubbed providers. Phase 10B adds saved investigation reads, polling, URL restoration, and typed support-operator decisions with durable authority/audit and distinct publication/execution outcomes; its fresh PostgreSQL verification remains blocked and provider non-delivery semantics remain unproven. Phase 10C adds durable sanitized milestones and authenticated resumable fetch streaming through the existing backend; polling remains the fallback. Phase 11 adds an offline deterministic report runner and contract probes; its checked-in conservative no-model control misses diagnosis and held-out retrieval targets, and does not measure real-model acceptance/cost/latency or live eligibility. Optional Phase 12 implements an advisory semantic judge with an atomic rubric, swapped-order comparison, explicit inconclusive flags, bounded live pilot, and failure-usage replay fix. Eight calls used 12,880 tokens; two of four pairs were conclusive, surrogate agreement was 1/2, and one pair had invalid output. Human calibration and useful-signal evidence remain pending; the judge grants no authority. Phase 14A adds operational controls (feature switches, per-actor budgets, runtime limits, access/audit, and the operational runbook); local fixture verification is complete (offline 15/15, PostgreSQL/restore 7/7, operational drills 3/3, Kafka recovery 17/17, Linux SIGTERM and broker restart passed); production DB role grants, organizational retention, encrypted backup/restore, and paid-provider behavior remain unverified. Live replay remains disabled, the live agent schema still needs its controlled migration, and production reverse-proxy delivery was not available for verification. Use [architecture.md](./architecture.md) for the authenticated service boundary, [current-state.md](./current-state.md) for implementation details and limitations, [ai-dlq-master-plan.md](./ai-dlq-master-plan.md) for phase scope, and [AI/phase14a-operations.md](./AI/phase14a-operations.md) for operational configuration and runbook.

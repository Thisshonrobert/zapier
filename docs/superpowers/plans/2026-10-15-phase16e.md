# Phase 16E implementation plan

Execute inline with executing-plans and TDD. Preserve the current checkout and unrelated edits; no Git integration actions.

**Goal:** Deliver the engineering workspace: a designated engineer opens `/engineering`, sees the escalations that support durably routed to engineering (after a reload or a service restart), inspects the authorized case with its append-only handoff history, and returns findings to support or resolves the case with an explanation. Unauthorized reads and writes are denied, and the workspace holds no replay authority.
**Spec:** `docs/AI/support-workspaces-and-dlq-lab-plan.md`, Section 3 (engineering boundary and revocation), Section 4 (escalate / return findings / resolve handoff rows), Section 7 (engineer view), and Phase 16E.
**Architecture:** Phase 16C already persists the durable workflow and exposes bounded `/engineering/...` routes. This phase adds the missing read model and the browser surface: a case-history projection on the engineering service (reusing the existing case read for its permission check, queue binding and access audit) and a two-boolean viewer capability endpoint so navigation reflects the account's current roles. No schema change, no new dependency, no replay surface.
**Stack:** Existing Bun, TypeScript, Express, Next.js, PostgreSQL/Prisma.

## Deliberate narrowings and deviations

- **No schema change and no new audit action.** The first draft added an `engineering_read_history` audit action; the live `TriageAccessAudit_action_check` constraint rejected it (`23514`). Rather than widening a 16C constraint for a synonym, the history read reuses `engineering_read_case`: it is the same authorized read of the same case, and the constraint stays as narrow as 16C defined it.
- **History events drop `metadata`.** `TriageCaseWorkflowEvent.metadata` is unbounded JSON written by other surfaces and is not needed for the human handoff trail, so the projection returns `null`.
- **Capabilities live under the triage router.** The spec places role-aware navigation in 16E, and the existing permission pattern is server-side, so `GET /api/v1/triage/viewer` was added there instead of widening the user route's contract. It exposes two booleans about the caller, never a directory.
- **No execution-evidence panel in the workspace yet.** The 16C `/engineering/.../failure-context` and `/execution-evidence` endpoints proxy the AI agent and remain available, but the workspace does not depend on the agent being up; case context, escalation reason and history come from durable application state. A later phase can surface the agent evidence without changing this read model.
- **`process`-free idempotency keys.** The client sends a browser `crypto.randomUUID()` idempotency key per action, matching the backend's `idempotency-key` header contract, so a double submit is a no-op rather than a second handoff.

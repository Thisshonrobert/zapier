# Phase 16D implementation plan

Execute inline with executing-plans and TDD. Preserve the current checkout and unrelated edits; no Git integration actions.

**Goal:** Deliver the owner failure and repair journey: an owner sees only their own failures with the correct Zap identity, step label, published customer-safe repair instructions and workflow status; the owner can edit the named action in place and submit repair completion, which returns the case to support. Stale edits are rejected and the original failure/replay ledger is left untouched.
**Spec:** `docs/AI/support-workspaces-and-dlq-lab-plan.md`, Section 3 (owner boundary, owner-safe projection), Section 4 (owner repair handoff rows), Section 5 (editing changes future configuration only), and Phase 16D.
**Architecture:** Additive bounded contracts for the owner projection. A new `TriageOwnerService` performs owner-scoped reads and the bounded action update inside Prisma transactions. Repair instructions are the operator-reviewed `customerInstructions` already persisted by 16C's `TriageCaseWorkflow`; no new mutable ticket state is introduced. Optimistic concurrency reuses the 16C pattern: the repair view carries an action token derived from current action metadata, and a mismatched token is rejected with 409 before any write.
**Stack:** Existing Bun, TypeScript, Express, Next.js, PostgreSQL/Prisma. No new external dependencies, no schema change.

## Deliberate narrowings and deviations from the first draft of this plan

- `/cases/:caseId/actions/:actionId/repair` replaced a pair of helper routes; one route
  carries both the token and the fields, which keeps the stale check and the write together.
- `apps/primary_backend/route/zap.ts` and `apps/frontend/src/hooks/useZaps.ts` were **not**
  modified. A general Zap action mutation would authorize edits outside a failure case and
  outside the repair window; the case-bound endpoint is narrower and satisfies the phase.
- `apps/frontend/src/lib/owner-repair.ts` was folded into `src/types/owner.ts`, so the draft
  helpers and the types they operate on live together.
- One pre-existing defect was found and fixed while testing: `POST /cases/:caseId/repair-acknowledgement`
  accepted a repair completion when the workflow row was missing (`if (current && ...)`).
  It now fails closed with 409, covered by a new HTTP test.
- The 16C migration had never been applied to the local development database. It was applied
  through `pg` (the Prisma schema engine cannot spawn under the sandbox) and recorded in
  `_prisma_migrations` with its real checksum, so `prisma migrate deploy` stays idempotent.

## Known limits recorded at planning time

- `frontend#lint` has pre-existing failures in untouched files and `frontend#build` cannot run under the local sandbox (`spawnSync cmd.exe EPERM`); both were already reported as baseline/blocked in the 16C handoff.
- The stale-edit guard is an optimistic token derived from current action metadata rather than a database version column, so it needs no migration; a conditional `updateRaw` on the token closes the read-then-write race.

## Runtime verification against Docker PostgreSQL and Kafka (post-implementation)

PostgreSQL on `localhost:5432` and Kafka on `localhost:9092` are running in Docker and both ports are reachable. Applying the real database to the suite found **three defects that the fake-database tests could not**:

1. **Every repair save failed in production.** `$transaction` callbacks receive a transaction
   client whose model delegates live under `tx.action`, not `tx.updateMany`. The service called
   `tx.updateMany`, so every save threw `tx.updateMany is not a function`.
2. **The conditional write could never match.** Prisma compares a JSON field structurally, so
   `metadata: { equals: <sha256 token> }` never matched any row. It now performs a raw
   `UPDATE "Action" ... WHERE metadata = <loaded metadata>::jsonb`, which is both correct and
   atomic, and is asserted by a test that simulates a concurrent writer between read and write.
3. **`listFailures` raised a PostgreSQL error.** `GROUP BY "caseId"::text` left the other selected
   columns ungrouped (`42803`). It now uses `SELECT DISTINCT ON (retry.id)` with an outer ordering,
   which is the correct construct for "one row per case, newest first".

Both fixes are covered by the new `triage-owner-db.integration.test.ts`, which runs the whole
journey against real PostgreSQL: owner scoping, the repair window, the durable metadata write,
the stale/racing writer, credential preservation, and the workflow transition with its
append-only event and access audit.

Kafka-broker-dependent coverage is **blocked by the Bun runtime, not by this code**:

- The broker itself is reachable — a direct kafkajs diagnostic against Docker produced and
  consumed a message successfully.
- `bun test` on `replay-recovery.integration.test.ts` fails in `node:assert`'s
  `partialDeepStrictEqual` (`expectedCounts.@set is not a function` — a Bun Set-implementation
  gap), then kafkajs metadata requests time out, then the Bun process segfaults.
- `node --test` cannot run it either: the runner spawns a child process and the sandbox returns
  `EPERM`.
- The broker-independent half of replay durability, `replay-db.integration.test.ts` (33 tests),
  passes against real PostgreSQL.
- PostgreSQL-backed integration tests need `DATABASE_URL` and could not run here.

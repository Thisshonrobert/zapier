# Phase 14A operational controls (internal, read-only first)

This describes the supported single-instance investigation runner. It does not authorize external rollout or live replay. `REPLAY_RELEASE_READY` remains false in code. Use stub providers for operational drills.

## Configuration and limits

- Set `INVESTIGATION_ENABLED=true` on both primary backend and AI agent to admit and run queued investigations. The default is off. Stop new work by setting it to `false` and restarting both services. The agent drains its current poll before closing the model and database pools; a forced termination leaves the 90-second lease available for retry, at most three attempts.
- Set `REPLAY_INTENT_ENABLED=true` only to allow an operator to record a replay request. The default is off. This never enables dispatch: `REPLAY_ENABLED` is also gated by the hard-coded release check. Turning either switch off prevents new work but cannot unsend an accepted external action.
- Configure `TRIAGE_ALLOWED_ORIGINS` as a comma-separated list of exact browser origins. The backend defaults to `http://localhost:3000`; nonbrowser requests without an Origin header still use authentication. Keep `AI_AGENT_URL` and `PRIMARY_BACKEND_URL` on private service addresses. The AI HTTP listener binds to loopback. Use a 32-byte-or-longer random `TRIAGE_SERVICE_SECRET` shared only by these two services. Never expose `GEMINI_API_KEY`, service secret, or database URLs to the frontend.
- The agent requires `AI_AGENT_DATABASE_URL` when enabled. Run migrations with a dedicated migration role, then use a runtime role restricted to DML in `ai_agent` (including checkpoint tables). The primary backend role owns its application tables and audit writes; do not give the agent role approval or replay table privileges. Test these grants before enabling the switch. `DATABASE_URL` is not an agent runtime fallback.
- Defaults per rolling 24 hours: 20 new requests per subject owner and per operator; a maximum of two simultaneous claims per subject owner and per operator; 256,000 reserved model tokens and 100 reserved cents per subject owner and per operator. The current single-process poll loop runs one claim at a time; the database limits also protect multiple runner processes. Each claimed attempt reserves 64,000 tokens and a conservative cost ceiling; retries reserve again and failed calls are not refunded. Configure `INVESTIGATION_OWNER_REQUESTS_PER_DAY`, `INVESTIGATION_OPERATOR_REQUESTS_PER_DAY`, `INVESTIGATION_OWNER_CONCURRENCY`, `INVESTIGATION_OPERATOR_CONCURRENCY`, `INVESTIGATION_OWNER_TOKEN_BUDGET_PER_DAY`, `INVESTIGATION_OPERATOR_TOKEN_BUDGET_PER_DAY`, `INVESTIGATION_OWNER_SPEND_CENTS_PER_DAY`, and `INVESTIGATION_OPERATOR_SPEND_CENTS_PER_DAY`. Production supports `gemini-2.5-flash` standard pricing only. Set `INVESTIGATION_INPUT_USD_PER_MILLION_TOKENS` to at least 0.30 and `INVESTIGATION_OUTPUT_USD_PER_MILLION_TOKENS` to at least 2.50; missing or lower rates fail startup. The cost reservation uses the larger rate for all 64,000 reserved tokens and rounds up to cents (16 cents at these floors). Official [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing) on 2026-10-04 lists output including thinking at $2.50 per million and input at $0.30 per million for the standard tier. Reverify pricing before paid rollout. The ledger is a conservative reservation, not a provider invoice.
- The runtime limits one model generation per attempt, 2,048 output tokens (including thinking), 16,000 combined prompt characters, a 15-second model deadline, 60-second investigation deadline, 2-second backend tool deadline, 10-second PostgreSQL query deadline, and 5-second DB connection deadline. Before generation it calls `countTokens` on the exact `generateContent` request and denies calls whose counted input plus the 2,048 output ceiling exceeds 64,000; count failures deny generation. [Gemini thinking documentation](https://ai.google.dev/gemini-api/docs/generate-content/thinking) states that `max_output_tokens` includes thoughts and visible output; the [countTokens API](https://ai.google.dev/api/tokens) accepts a full `generateContentRequest` including system/tool steering. Request JSON is capped at 16 KiB. Backend-to-agent reads have their own 3-second/5-second deadlines. Scope tokens expire after at most five minutes. Configure provider egress timeouts and DB server statement limits consistently.

## Access, visibility, and retention

Only authenticated `User.isSupportOperator` accounts may select cases or act; revocation is checked again when a runner renews its owner-bound scope and during approval/replay validation. Case IDs and owner IDs are derived from the database, not operator JSON. Access and replay-intent writes are in `TriageAccessAudit`, authority changes in immutable application tables. Audit DB access is restricted to support/security roles. Do not log raw evidence, credentials, scope tokens, prompts, or provider responses. Evidence is redacted before agent use; reports expose sanitized outcomes and identifiers.

The private `GET /private/v1/investigations/status` requires the service secret and returns counts plus the oldest queued/stale timestamps. Alert when stale leases remain past 90 seconds, errors rise, or the oldest queued item exceeds the expected poll interval and budget window. Inspect `ai_agent.investigation` and `ai_agent.investigation_budget` with a privileged SQL account for a specific case; avoid dumping snapshot JSON into logs. The event stream serves seven days of history while immutable event rows remain in the database. Retain authority/audit rows and snapshots under the organization's approved policy and encrypted DB backups; do not purge immutable authority rows independently of their foreign keys. Budget reservations enforce a rolling 24-hour window; rows older than 30 days may be selected for a separately approved archive, but this phase has no automatic deletion. Set an explicit production retention and encrypted archive policy before external rollout.

## Outage, restore, and rollback drill

Test with stub model and action providers. Deny and revoke operators, change case ownership, cross-bind IDs, repeat idempotency keys, turn both switches off, interrupt the process mid-investigation, and simulate model, PostgreSQL, and Kafka unavailability. An agent failure must leave no replay publication. Kafka failures remain subject to the existing replay dispatcher/worker recovery tests, with live replay still disabled.

For backup, stop new investigation and replay-intent work, quiesce writes, then take an encrypted, transactionally consistent PostgreSQL backup of the **whole application database**, including `ai_agent`, `TriageApproval`, `TriageProposal`, `ReplayRequest`, `ReplayExecution`, and `TriageAccessAudit`. Preserve the migration history, roles/grants, and the exact backup timestamp. Do not restore authority tables one at a time. Restore to an isolated database with network egress to Kafka/providers blocked. Apply no new replay dispatch on restore. Compare row counts and immutable IDs, approval expiry, actor/owner bindings, replay request uniqueness and consumption, access audits, checkpoint thread IDs, and revocation state against the backup manifest. Re-run dry-run policy checks and an idempotent request with stub providers; confirm no duplicate replay. Only then plan a controlled cutover with the switches still off. The local fixture below exercises an isolated schema archive round trip; it does not verify encrypted whole-database backup, role metadata restore, or a deployment cutover.

## Disposable local fixture

`scripts/phases/phase14a/compose.yaml` uses a separate `zapier-phase14a` Docker project with PostgreSQL 16 and Kafka 3.7.1 on loopback ports 54329 and 19092. `fixture-env.mjs` creates a new random database for each invocation, pins both agent/backend DB variables to it, blanks paid-provider/observability credentials, and drops the database afterward. It never targets the application Compose volumes. Start and clean up only this project:

```sh
rtk proxy docker compose -f scripts/phases/phase14a/compose.yaml -p zapier-phase14a up -d --wait
```

Run `bunx prisma generate --schema packages/db/prisma/schema.prisma` before the Node recovery suite if the local generated client is stale; the repository's `test:replay-recovery` script does this. Generated client files are test artifacts, not part of the Phase 14A bundle. The drills assert real role denial on application authority tables, event visibility and immutable history, durable budget/retry behavior, PostgreSQL outage recovery, POSIX idle-service SIGTERM completion, a delayed stub investigation draining before the next claim, Kafka broker restart/committed offset recovery, and isolated schema dump/restore. Windows child `SIGINT` is treated as forced termination, not graceful drain. They do not establish production grants, organizational retention, encrypted backup, paid-model behavior, or live replay readiness.
